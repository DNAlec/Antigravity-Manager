# 配置保存与冲突处理

`gui_config.json` 的 `config_revision` 是服务端维护的单调递增版本。旧文件在首次加载时自动迁移；客户端不应自行增加、删除或替换这个字段。

## Web / CLI 管理客户端

1. 使用已有管理鉴权调用 `GET /api/config`，保留返回配置中的 `config_revision`。
2. 在这份配置上修改所需字段，以 `{ "config": <完整配置> }` 调用 `POST /api/config`。
3. 成功响应是规范化后的完整配置，包含新版本号。后续编辑以该响应为基线。
4. `409` 与 `CONFIG_CONFLICT:` 表示配置已被其他操作修改。重新读取并核对冲突，只重做用户原本要改的字段。不要把新版本号移植到旧完整快照后重试，否则会重新引入覆盖风险。

Tauri 的 `load_config` / `save_config` 遵循同样约定；冲突通过命令错误传播。没有版本号的旧完整保存客户端必须升级。启动、停止等独立命令会推进版本，调用后应刷新配置。

## 前端约定

配置写入统一通过 `useConfigStore`：字段操作用 `updateConfig`，独立持久化命令用 `mutateConfig`，完整表单用 `saveConfig`。不要绕过队列直接调用配置服务。等待 Promise 完成后才显示成功；失败会回读服务端状态，并取消基于失败状态排队的旧写入。恢复期间新写入会被拒绝，用户可在恢复后重试。

需要未保存草稿的面板使用 `useConfigDraft`。无关配置更新可合并；同字段冲突保留草稿并阻止完整保存，直到用户明确丢弃并重新加载。不要在异步回调中恢复旧完整快照。数组作为整体处理，避免自动合并产生重复或误删。

健康检查结果是运行状态，不应以完整配置保存。结果发布时校验代理 ID、地址、认证及检查地址，丢弃已经编辑过的连接的旧结果。

## 后端约定与边界

完整保存使用 `save_app_config_versioned` 比较版本；独立字段修改使用 `update_app_config` 在同一磁盘锁内读取、修改、原子写入。涉及运行态发布时，先获取有超时的 `lock_config_operation`，落盘成功后再热更新，避免并发发布顺序倒置。

独立字段接口保证不覆盖其他配置字段；这些接口没有客户端版本前置条件，同一字段的多客户端修改仍按服务端处理顺序生效。磁盘锁和发布锁是进程内锁，不支持多个管理进程共享同一数据目录进行并发写入。磁盘提交后进程崩溃或网络中断可能让客户端无法确认结果；此时应重新读取，不自动重放旧快照。
